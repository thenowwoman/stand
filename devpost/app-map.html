Stand App Map

A compact reference for the current proof-of-concept: a mobile-first profile builder that can clarify a vague description before turning it into structured services and opportunity ideas, with optional browser voice controls.

What the app does

The app accepts a short text prompt, optionally lets the user dictate it, asks up to three AI-generated follow-up questions one at a time when helpful, combines the answers with the original text, then shows likely skills, pricing-friendly service packages, a client-ready profile, and opportunity ideas. The generated bio can be read aloud on request. Speech stays in the browser; it is not sent to the server. The app keeps the profile and an in-progress question conversation in localStorage so a user can return without an account.

Reference route

  1. Start here: src/App.tsx — prompt state, follow-up answers, combining user details, and browser persistence.
  2. Question step: requestFollowUp() in src/App.tsx calls /api/follow-up; server/follow-up.js asks one question at a time and returns a fallback signal if the model fails.
  3. Profile output: generateProfile() in src/App.tsx sends the combined description to /api/profile and retains existing fallback behavior.
  4. Voice controls: toggleVoiceInput() and toggleReadAloud() in src/App.tsx use optional browser speech APIs; unsupported browsers retain the typed flow.
  5. Visible output: src/styles.css — mobile-first cards, service package styling, and the profile/opportunity panels the user sees.

To change this, start here

  • Change question flow: edit requestFollowUp() in src/App.tsx or the question prompt in server/follow-up.js.
  • Change the generated skill/service fallback: adjust buildFallbackData() in src/App.tsx.
  • Change the visual feel: update the card layout and spacing in src/styles.css.
  • Change the code-inspired welcome and responsive flow diagram: update .welcome-opening and .journey-map in src/styles.css.

Practice to reuse

This project shows a useful pattern: when a requirement starts vague, define an observable result early and test it in the browser. The app’s core acceptance criterion is “a short description turns into a credible client-ready profile,” and it is validated by the actual build and a browser check rather than just a code review. The same approach can help on other projects: write the user-visible result first, then build only the logic needed to satisfy it.
